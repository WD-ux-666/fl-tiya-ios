## Isolation and architecture
The new scheme uses Debug, an explicit launch environment flag FLTIYA_LOCAL_STOREKIT_TESTING=1 and a standalone .storekit file. Archive/Profile use Release, without local test launch configuration. A DEBUG and non-DEVELOPMENT_PREVIEW guarded factory chooses a local repository, never a Supabase payment repository, only when the flag is set. The local payment identity is available only for a server-verified development cohort. Release cannot activate the local implementation via environment.

Reuse the existing StoreKit storefront and PaymentStore lifecycle. Add Xcode as an explicit payment environment. Pass structured already-verified PaymentTransaction facts to repository delivery rather than asking the local repository to trust a raw decoded JWS. Local validation independently checks environment, exact account token, known local product ID, consumable/quantity and transaction identity. Supabase delivery refuses local/Xcode transactions before any network request. The local journal writes atomically before acknowledgement/finish and holds no raw JWS, access code or Auth token. A storage failure before the atomic commit never grants or finishes; post-commit permission hardening is best-effort. Repeated transaction IDs cannot increase the balance twice. Existing generation checks protect account switching and late callbacks.

Local StoreKit product IDs are dedicated test IDs and never replace server/App Store Connect product mappings. The .storekit file is a scheme testing input, not a runtime resource distributed with the app. Native receipt verification remains StoreKit VerificationResult. Real Apple server delivery and Supabase balances are not validated by this local test. Observed full revocations remove the credit once; stale callbacks cannot restore it. Offline historical refund reconciliation, partial refunds and refund reversals are outside this local harness.
