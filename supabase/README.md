## Client contract

All table/RPC access requires an eligible Auth identity, an active application account and an existing `auth.sessions` row matching the JWT `session_id`. Apple production requires an Apple identity and a database OAuth AMR claim for that exact session; anonymous experience production requires immutable server attestation, actual Auth anonymity and database anonymous AMR; development requires a confirmed email identity matching an enabled, unexpired server reservation. Both actors and visible targets must be eligible and share the same immutable cohort. The client carries only the project URL and publishable key plus its user access token. No `anon` table or RPC access is granted.

| Table | Client access and columns |
| --- | --- |
| `profiles` | Select visible active profiles; update own `handle`, `display_name`, `bio`, `avatar_path`. Columns: `id` UUID, `handle`, `display_name`, `bio`, nullable `avatar_path`, `created_at`. Auto-created after Auth signup, with a neutral generated handle. |
| `games` | Select only. `id` text slug, `name`. First ID: `zenless-zone-zero`. |
| `game_cards` | Select visible owners; insert/update/delete own. Composite key `user_id` UUID + `game_id` text; `player_name`, nullable integer `days_played`, `progress` text. All values are manually entered. |
| `friend_requests` | Select own incoming/outgoing requests. `id`, `sender_id`, `recipient_id` UUID; `status`: `pending/accepted/declined/cancelled`; `created_at`. Mutations require RPC. |
| `friendships` | Select own visible relationships. Canonical UUID pair `user_low < user_high`. Mutations require RPC. |
| `conversations` | Select own visible conversations. `id`, `user_low`, `user_high` UUID; `created_at`. Exactly one conversation per pair, created when the recipient accepts. |
| `messages` | Select own visible conversation messages. `id` client UUID, `conversation_id`, `sender_id`, `body`, `created_at`. Send through RPC. |
| `blocks` | Select only own rows: `owner_id`, `blocked_id`, `created_at`. Block through RPC. |

Mutation RPCs return one JSON object; discovery returns an array. Decode the server response:

| RPC arguments | Return |
| --- | --- |
| `send_friend_request(target_user_id: UUID)` | Request fields: `id`, `sender_id`, `recipient_id`, `status`, `created_at`. Repeated outgoing pending requests return the same row. A reverse request errors with `incoming_request_exists` and requires explicit acceptance. |
| `respond_friend_request(request_id: UUID, accept: Bool)` | `request_id`, `status` (`accepted` or `declined`), nullable `conversation_id`. Only the recipient may respond. |
| `block_user(target_user_id: UUID)` | `blocked_user_id`. Cancels pending requests and removes friendship atomically. Both sides immediately lose conversation/media/profile access through policies. |
| `send_message(target_conversation_id: UUID, message_id: UUID, message_body: String)` | Message fields. Trimmed text must contain 1–2000 characters. Reuse the same message UUID on retry; a different payload with that UUID errors. Current accepted friendship and no block in either direction are required. |
| `discover_players(search_query: String)` | Array of profile rows, excluding self, inactive accounts and either direction of blocking. Case-insensitive literal substring search on handle/display name; `%`, `_` and backslash are literal text. Empty query returns up to 50 profiles, ordered by handle/UUID. |

Nonparticipants, inactive/deleted actors, invalid sessions and either direction of blocking fail closed. Pair advisory locks serialize request acceptance, blocking and sending; row locking keeps an actor active during a mutation. Direct friendship, request, conversation, message, balance, entitlement and review writes are denied. API wrappers are `SECURITY INVOKER`; audited privileged implementations and helpers remain in the non-exposed `private` schema with explicit signature grants and empty `search_path`. Never expose `private` in Data API settings.

## Media and other foundations

- `video_posts` supports real pending submissions only. Insert `id`, `owner_id`, `game_id`, `caption`, `video_path`, optional `thumbnail_path`. Paths must start `<owner UUID>/<post UUID>/`. Upload to private bucket `clips` with `upsert: false` **after** inserting the pending post. The owner can read pending/rejected posts; other visible users can read approved posts only. Clients cannot update/delete objects or change post status, including after approval. A trusted reviewer must inspect the uploaded bytes and matching thumbnail, then record `private.video_reviews` and update status/`approved_at` in one database transaction. Bucket MIME/size checks alone are not a media content inspection.
- `avatars` is private. Insert a new object under `<owner UUID>/<unique filename>` with `upsert: false`, then set the own `profiles.avatar_path`. Existing names are immutable. Only the profile's current avatar is readable. Unused uploads need trusted cleanup.
- Media reads use the current user Authorization header. The pinned Swift SDK uses `storage/v1/object/<bucket>/<path>` for authenticated GET; this route was verified with complete byte/hash readback for the imported clips. The explicit `storage/v1/object/authenticated/<bucket>/<path>` route is also documented by Storage. Operation-aware policies deny signing, listing, replacement and deletion. Do not introduce public buckets or signed URLs for owner-only pending material: a signed URL remains usable until expiry and is not revoked by logging out.
- Upload admission allows standard `object.upload` only. Signed upload capabilities, resumable/S3/copy operations and replacement require a separately reviewed design; they are deliberately not authorized by these policies.
- `guides` is read-only to users and exposes only `published` rows with required HTTPS source, source name and attribution. No ingestion, copied article content or sample guide is enabled.
- `wallets` starts at a real zero row. The follow-up `schema/payments.sql` adds service-only, idempotent Apple delivery/refund accounting, separate Sandbox wallets and nine inactive draft packs. Clients still have no economic write grant. See [payments](PAYMENTS.md) for Edge endpoints, the direct Apple HTTPS verification boundary, setup and actual validation limits. Real Apple products/keys/login remain unconfigured. Avatar-frame spending/equipping, rewards, transfer and cash-out are not implemented.
- Voice/video signaling, selected-session authorization and room/token revocation cleanup are now deployed, with native LiveKit integration source. Live media remains unavailable until a LiveKit Cloud project is configured and two-device native testing is completed; see [CALLS.md](CALLS.md). Guide discovery is deployed separately; review administration and account deletion worker remain pending.

## Deployment and verification

1. Confirm the authorized project reference and inspect its current schema, Supabase/Postgres versions, existing Storage policies and `storage.allow_any_operation(text[])` support. This source deliberately fails if its application tables/buckets already exist; review and create a real follow-up migration rather than blindly replaying it.
2. Configure native Apple Sign In for the real App ID, and enable only Apple among OAuth providers. Anonymous Auth is enabled for the separately approved device-account entry; keep its server attestation/session restrictions. See [experience authentication](../docs/experience-auth.md). Email/password is currently required by the reserved development workflow; to retire that workflow, disable the reservations and remove its endpoint before disabling password sign-in. A public unreserved email signup cannot access application data. Keep the Auth signup trigger minimal; its failures intentionally prevent incomplete accounts. Test a first Apple signup and a returning Apple login. Never copy email or Apple subject into public profiles and never use `user_metadata` for authorization.
3. Apply the reviewed source with remote `apply_migration` using a descriptive name, or use the installed CLI's migration workflow after consulting its help. Record the actual returned remote migration version; do not invent one. RLS, grants, functions and bucket policies belong in the same deployment. Confirm `private` is not an exposed schema.
4. Run security/performance advisors and a real allow/deny matrix with separate Apple users A, B and C plus `anon`: self/profile writes; cross-user game-card denial; pending/reverse/recipient-only requests; simultaneous accept/block/send; accepted and nonfriend messages; message retry/conflict; unrelated conversation IDs; blocks in both directions; pending/rejected/approved clip reads; signing/listing/upsert/replacement denial; direct balance/entitlement/status writes; revoked session; suspended and deleted actor with the original unexpired JWT. Also check grants and indexes. Static review is not evidence that RLS or SQL executes correctly.
5. Account deletion must first atomically set `private.accounts.state = 'deleting'` to remove data access, revoke sessions, remove owned Storage objects through the Storage API, then hard-delete the Auth user through Admin Auth. Storage ownership can prevent Auth deletion. Retry incomplete cleanup server-side without restoring account access; do not delete Storage metadata with raw SQL. Public profile references cascade; private financial transaction uniqueness is retained without a profile reference. Apple authorization revocation and legally appropriate financial retention must be implemented before release.
